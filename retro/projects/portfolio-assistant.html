How I built a chatbot over my portfolio notes

I built a separate interactive portfolio where people can ask about my work. The hardest decision was how much machinery a small set of notes really needed.

What a visitor might want to ask

Someone skimming my portfolio might want to know whether I'd used a particular tool. I built a separate interactive version where they could ask directly and get an answer based on my notes.

Opening the feature to visitors also meant thinking through request costs, sensitive input, and what I wanted to store from a conversation.

How I looked up the right notes

Retrieve relevant notes

I classify the question to pick up its topic and any named tools or projects. Then I score the notes by keyword, tag, and alias overlap and pass the relevant material to the response model.

Start with a small-data approach

I considered vector search. For a collection this small, the scored lookup gave me a straightforward way to find a few passages and see why each one came back.

Bound public requests

I added input checks, device and IP restrictions, database-backed minute and day limits, a global daily model-call cap, and a Python safety service using Presidio. Those checks reduce exposure to abuse and sensitive input.

What happens to a message

I encrypt stored message text with AES-256-GCM using a key supplied by the client session. The encryption uses a fresh initialization vector and an authentication tag. The route checks for a valid key before proceeding, and decryption verifies the tag.

That protects stored text. During a request, the application still reads the message and sends the necessary prompt to the model provider.

The request limits cap usage. Running the feature still depends on how the deployment is configured and whether the provider is available.

When I'd revisit retrieval

The result is one request flow that looks up portfolio notes, checks incoming requests, generates an answer, and encrypts the message text it stores.

I came away with a better starting point for retrieval. I'd count the notes, try the kinds of questions visitors are likely to ask, and see where the lookup falls short before adding a new search system.
