The problem

A portfolio can contain an answer without making it easy to find. I built a conversational version that responds to questions about my experience and projects using my own knowledge base. This case study describes that separate application; the plain HTML website you are reading does not run a chatbot.

The challenge was not just generating an answer. It was selecting relevant material, controlling public API usage, handling sensitive input, and deciding what could be stored.

Keeping retrieval proportional to the dataset

Retrieve relevant notes

The implemented approach uses a small structured knowledge base and scored keyword, tag, and alias overlap. A classification step helps identify the question's topic and named tools or projects before the relevant material reaches the response model.

Start with a small-data approach

This keeps retrieval inspectable for a compact collection of portfolio notes. A vector-search design was considered, but the working small-dataset approach did not need the extra infrastructure merely to retrieve a handful of relevant passages.

Bound public requests

The server-side request path includes input checks, device and IP-based restrictions, database-backed per-minute and per-day limits, a global daily model-call ceiling, and a Python safety service using Presidio. These layers reduce exposure; they are not a claim that prompt injection or every sensitive-data case has been solved.

Conversation storage and boundaries

Stored message content uses AES-256-GCM with a client-supplied session key. Encryption creates a fresh initialization vector and retains an authentication tag; decryption checks the supplied key and tag. The route rejects missing or malformed session keys before proceeding.

This protects the stored transcript content under the implemented key-handling model. It does not make model requests end-to-end encrypted: the application still has to process the message and send the necessary prompt to its model provider.

Rate limits and a daily request ceiling put operational bounds around the public feature. Configuration and provider availability remain deployment concerns rather than properties a static case study can guarantee.

What I learned

The project connects retrieval, generation, safety checks, and encrypted logging in one request flow. The useful lesson was architectural restraint: start with the size and structure of the actual knowledge base, then add retrieval infrastructure when the simpler system has a demonstrated limitation.

The interface can stay simple while the backend is explicit about its boundaries. That same principle carries into this HTML site: the articles explain the work, and the browser does not need a model call just to show it.
