The problem

A slide deck is an outline, not a spoken script. Turning it into something natural takes a second round of preparation, and losing your place during delivery is a separate problem. I built Cueframe to connect those steps: import a deck, prepare a script, edit it, present privately, and review the timing afterward.

The important product boundary is presenter control. AI suggests a draft; the presenter controls wording and pace. The audience sees the slides, while the script and private cues stay with the speaker.

How I built it

Keep a local working copy

The working copy lives in IndexedDB: projects, slide images, script versions, and presentation sessions. PDFs are rendered with pdf.js; PowerPoint files are parsed from their underlying XML. PowerPoint previews are simplified, so exporting a PDF remains the better path when exact slide visuals matter.

Bound the AI pipeline

The writing pipeline separates analysis, deck context, outline, and writing, with a local planner assigning a word budget from the speaking rate and time available. Analysis begins during import. Writing works in batches of four slides with three requests in flight, rather than sending the whole deck through one unbounded request.

Validate before saving

Structured outputs carry slide IDs. Missing, duplicated, or foreign IDs are rejected, and a complete draft is committed only when all slides are valid. A source fingerprint detects intervening edits, while earlier script versions remain available. In the Lexical editor, an AI rewrite is a proposal to accept or discard.

Separate presenter and audience

The presenter window calculates scrolling from words per minute and supplies slide timers, a reading line, and a cancelable advance countdown. The audience window receives slide state through BroadcastChannel; script text and cues do not cross that channel.

Make sync optional

Optional cloud sync mirrors local changes to Firestore and Storage. Each device keeps a sync cursor, and an IndexedDB outbox retries unconfirmed writes. On the server, AI allowances reserve a request's maximum token use before dispatch so parallel requests cannot spend the same remaining allowance.

Evaluation and tradeoffs

I compared writing approaches using frozen inputs, held-out decks, and blinded comparisons with the presentation order swapped. An earlier, heavier writer-and-reviewer variant won both orders in 13 of 15 completed held-out pairs. However, three of 18 attempts were rejected by its source gate; its generation token use was roughly twice the baseline and median latency rose from 8.859 to 26.76 seconds on three-slide fixtures.

Those results describe a historical experimental variant, not a measured production error rate or validation of the current pipeline. User feedback pointed to paraphrasing and spoken summaries, so routine generation now uses a versioned writing guide and local advisory checks instead of automatic model review and repair passes.

CI runs unit and API checks, security-rule tests, and browser journeys using a deterministic demo provider. One browser test checks the audience privacy boundary. These tests exercise the workflow without spending AI credits; judging real writing quality remains a separate evaluation task.

What the project delivers

The implemented loop covers import, setup, generation, editing, presentation, and timing review. Cloud sync and AI are optional, so the core workspace remains usable without an account or a model key. A hosted, invite-gated pilot is the intended rollout rather than an established public launch.

My main takeaway: a stronger model score is only useful when it measures the problem users actually have. A heavier evaluation winner can still be the wrong default if it adds delay and cost to a workflow that mainly needs better writing instructions.
