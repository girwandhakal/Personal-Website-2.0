The problem

A medical bill, an explanation of benefits, and an insurance policy describe related information in different formats. Even after understanding the balance, someone still has to work out what a payment would mean for their cash flow. ClearPath connects those documents and financial context in one prototype.

I built the full-stack application, including more than 20 API routes supporting document handling, assistant conversations, cost estimation, financial context, and scenario planning.

From uploaded document to usable records

Turn documents into records

The document workflow stores an upload, extracts text, and asks the AI layer to classify it as an insurance plan, medical bill, or explanation of benefits. The result is then projected into normalized Prisma records, rather than leaving every downstream feature to interpret a free-form response again.

Make reconciliation inspectable

The synchronization code normalizes provider names, dates, and numeric amounts while retaining extracted notes and source information. Bill-to-EOB reconciliation uses transparent provider, amount, and date comparisons. It can distinguish missing EOBs, amount mismatches, provider mismatches, and service-date mismatches. Users can also link documents manually.

Build the assistant’s context

When someone asks the assistant a question, a context builder assembles relevant insurance, document, financial, and conversation information. The model can then explain options using a defined context packet instead of receiving disconnected documents.

Test affordability in the sandbox

The Plaid integration operates in the sandbox. It supports account and transaction sync, normalized financial records, and affordability analysis. Cost estimation compares care settings, and scenario planning explores payment-plan tradeoffs and other options using the available context.

What is demonstrated, and what is not

This is a working development prototype with SQLite persistence, seeded financial personas, sample documents, and manual verification utilities. Some screens combine persisted data with configured or mock helpers. It should not be presented as a deployed financial service or as evidence of real patient savings.

The repository does not currently contain a formal automated test suite. Its documented verification includes a production build and manual API and parsing harnesses. That is a clear next engineering boundary for extending the project.

The engineering lesson

The main contribution is the path from unstructured documents to linked records and context-aware explanations. Document reconciliation is a distinct layer, not something to hide inside a chatbot prompt.

Data quality determines how useful the final explanation can be. A fluent response cannot repair a mismatched provider, an incorrectly parsed amount, or an EOB linked to the wrong service date. Those decisions need inspectable rules and their own validation.
